How the toolkit reaches a result.

The site uses focused, explainable checks instead of pretending to reproduce every part of a search engine, browser, crawler, or security scanner.

Browser-first by design

Many tools parse source text directly in the browser. This keeps routine checks simple and makes it clear what information is being analyzed. DNS tools use browser-accessible DNS-over-HTTPS requests because a DNS resolver is required to answer public DNS queries.

What a result means

A result is evidence for a next action, not a certificate. For example, finding a canonical tag confirms that a declaration exists in the supplied HTML; it does not prove that search systems will select that URL as canonical.

Why some checks need fallbacks

Normal web pages often restrict cross-origin browser reads. The Website Audit tool therefore offers a pasted HTML fallback rather than attempting to bypass browser security. Server-side crawlers, authenticated pages, redirect chains, request timing, and full network traces require capabilities outside this static browser implementation.

How severity is used

Severity is a triage aid. “High,” “medium,” and “low” indicate how prominently a signal is presented in this toolkit; they do not represent a universal ranking impact or a security classification.

Primary references

The site uses official technical and search documentation as reference material when defining checks and explanations. Key sources include Google Search Central documentation, Google's people-first content guidance, Google AdSense policies, Sitemaps protocol, IETF RFC resources, and W3C accessibility guidance.

Keeping the toolkit honest

When a check cannot establish something from browser-visible information, the interface says so. The goal is a useful next step with visible limitations, rather than a misleading score or guarantee.

Use the methodology in practice

Start with the Website Audit, then open the focused checker that matches the finding.
